# Building a limited geometry library in Zig

## Goals

1. Optimize for speed and correctness
2. Input geometries in Well-Known Binary
3. Target environment is WASM
4. Limited surface area is okay
5. Optimize for SIMD operations

## Where the project is (2026-09-10)

**One planar overlay engine**: the degenerate-tolerant Martinez-Rueda sweep line
in `src/sweep.zig`. The BVH-and-half-edge-graph engine that used to sit beside it
(`src/overlay.zig`, and the `backend` option and `geom_set_backend` export that
selected between them) has been **removed**. It lost on all 26 differential
workloads, by 1.01x to 2.99x, and never won one, while both passed 26/26.
Removing it took the WASM artifact from 175,702 bytes to 110,394, and 65,222
gzipped to 43,209.

The vendored Clipper2 tree and its bridge have been **deleted**. Nothing
third-party remains: the library is pure Zig, and `build.zig` links no C or C++.

## The sweep engine

Four departures from textbook Martinez-Rueda, all aimed at cadastral input:

- **Winding counts, not in/out parity.** Each layer carries an `i32` depth. Any
  number of polygons may be given per layer and they may overlap, stack or share
  edges. This deletes the SAME_TRANSITION / DIFFERENT_TRANSITION /
  NON_CONTRIBUTING edge classification entirely — adjacent parcels sharing a
  boundary contribute one bundle whose deltas cancel, rather than a case to be
  detected. It is also what makes n-ary union possible in a single pass.
- **No vertical special case.** Lexicographic (x, y) event order *is* the
  symbolic shear `(x, y) -> (x + ey, y)`. A shear has unit determinant, so every
  orientation predicate is unchanged while vertical segments gain a well-defined
  place in the status line. No coordinate is ever perturbed.
- **Exact predicates at every sign decision**, including a new paired
  `predicates.orient2` that filters two orientations sharing a base segment in
  one f64x2 determinant and drops to the exact expansion only per failing lane.
- **Structure of arrays** — endpoints in their own dense array, and an
  order-preserving u128 key per event so queue and status comparisons start from
  one integer compare.

The hard-won parts, all of which have regression coverage:

- Event order and status order must agree for collinear segments sharing a point,
  or a segment inherits winding from a predecessor it should never have had.
- A run of overlapping collinear segments bounds one region; winding propagation
  must step over the whole run, not treat its members as stacked.
- Subdivision must see every member of a run, and both sides' geometry must be
  snapshotted, so one shared line yields one crossing point for all of them.
- Exact duplicates are one geometric object and are divided together. Rounding
  puts a crossing on neither copy's line, so no later exact test can rediscover
  it on the twin.
- Each sweep point is processed as a batch — all closes, then all opens, then
  crossings — because a duplicate still sitting in the queue cannot be divided
  with its twin.
- Contours are settled in order of their leftmost vertex, which is not the order
  they are traced in: a pinch point pops its inner loop first.

## Verified status

The full differential suite is regenerated by `tests/compare/run.py` into
`tests/compare/generated/`, which is gitignored and rebuilt by every run. The
committed snapshots that used to sit under `docs/review-*` are gone; they
described a backend and an engine pairing that no longer exist.

`zig build test` runs 21 tests. All pass, in Debug and ReleaseSafe.

Against the 26 saved comparison cases (`tests/compare/generated/fixtures.json`,
source sha256 `764c0d0a…`) at `grid = 0`, with GEOS/Shapely as reference and
`run.py`'s own `metrics()` envelope — scratch re-runs at 3 repeats, not a
regenerated published report:

**Union is exact, and the last three failures were the reference.** All union
outputs are `is_valid` and symmetric difference against GEOS is `0.0` or
`<= 5.2e-13 m2` at 10 / 100 / 1000 / 4040 parcels. The three workloads that used
to fail did so on boundary Hausdorff alone; reconstructing every disputed vertex
with rational arithmetic settled it:

| | our max error | GEOS max error |
| --- | ---: | ---: |
| parcels-union-100 | **0.0** | 1.5e-6 m |
| parcels-union-1000 | **0.0** | 7.2e-6 m |
| parcels-union-4040 | **0.0** | 7.2e-5 m |

Every disputed vertex this library produced was exact to the last bit. The `f128`
intermediates in `predicates.intersection` resolve the nearly parallel parcel
edges that GEOS's f64 line intersector cannot.

The 209 m Hausdorff on `parcels-union-4040` was a second effect: the GEOS
reference contains 127 **filament rings**, one of them four coordinates, 1591 m
round and 1.5 mm2 in area. They carry no area, so symmetric difference never saw
them. This library emits 126 of the same rings — they are hairline gaps in
the source parcels, not artifacts — but a boundary Hausdorff cannot compare
something thinner than its own tolerance.

`tests/compare/run.py` now adjudicates instead of assuming: filaments are
compared out on both sides and counted per engine, and a Hausdorff exceedance is
resolved against exact arithmetic, failing whichever side is actually wrong. It
is symmetric and it discriminates — it still fails Rust Geo, out by up to 1.9 km,
and polyclip-ts and Turf where they are less accurate than GEOS.

**All 26 workloads pass, native and WASM**, against GEOS's 26, JSTS's 24,
Turf's 23 and Rust Geo's 18.

**155 of 158 applicable JTS Topology Suite assertions pass**, from JTS's own
test XML copied verbatim into `tests/jts/cases/` — including **120 of 120** for
the four boolean operations, across both the original overlay engine and
OverlayNG. 15 cases are skipped — 12 because their expected result is not areal,
and 3 from one case JTS's own `WKTReader` will not load — and counted separately
rather than scored as passes.

The 3 failures are all degenerate polygons — zero-area or under-four-point rings
that JTS buffers as linework and qdgeo rejects as invalid input. That is the
"failures are errors, not repairs" policy meeting JTS's leniency, so it is a
decision to take rather than a bug to fix. Running the suite is how it was
found; it also found and fixed a real one, below.

**Closed lines buffered wrong, and the JTS suite caught it.** A `LINESTRING`
whose ends coincide is ring linework, so its buffer is a band either side of
that ring. `bufferInput` was capping it as an open chain, which puts both caps
on one point and handed the overlay a curve it could not node — `NodingFailure`
on every closed line. It now offsets the ring and its reverse, guarded by
`erodedCompletely` so a wide band closes the middle instead of leaving a
spurious hole, and normalised for winding so a clockwise line does not come back
inside out. Pinned by a native test.

**SIMD is emitted and worth about nothing.** A `simd128` build carries 1,941
v128 opcodes against 5 without it, so the vectorisation is real; timed against
each other the two run within noise (0.97x–1.02x across four workloads). The hot loops are branch- and pointer-bound — BVH descent, status-line
search, hash lookups — and the exact-predicate fallback is scalar expansion
arithmetic that cannot vectorise. Two f64 lanes cannot move a profile shaped like
that. The vector forms stay because they are no larger and no slower, but the
goal of "optimize for SIMD operations" should be read as measured rather than
assumed. A real win would need batch predicate evaluation over structure-of-
arrays candidates, which is a large change against a 1.02x observed ceiling.

**WASM is fixed and import-free.** `zig build wasm` compiles again — the break
was `std.debug.print` dragging `std.posix` into a
`wasm32-freestanding` target. The artifact is 110,394 bytes stripped (43,209
gzipped), declares no imports at all, and needs no WASI host. `tests/wasm.test.mjs`
instantiates it with an empty import object and asserts the import list is
empty.

**Measured against Turf 7.4.0 and polyclip-ts 0.16.8** (both already the current
npm releases). Union, median of 5, all four engines timed in the same Node

All five committed fixtures pass. All 26 workloads produce valid
output with no errors; the three still marked failing are unions, on boundary
Hausdorff only, with zero or `5e-13` symmetric difference. Overall 23 of 26
against turf's 20 and GEOS's 26.

Two departures from JTS, both deliberate:

- **Input simplification is off.** JTS simplifies at `0.01 * distance` because its
  noder needs the help; measured here it costs exactly that much accuracy —
  worst-case Hausdorff against GEOS goes from `2e-6 m` to `1.1e-2 m` at a 2 m
  buffer — and fixes nothing this construction cannot already do. Kept as
  `BufferOptions.simplify_factor`, defaulting to 0.
- **No reduced-precision retry ladder.** It was not needed, so "failures are
  errors, not repairs" still holds.

`isErodedCompletely` is copied from JTS and is load-bearing: a ring narrower than
twice the erosion distance offsets to a curve that has turned inside out, still
closed and still wound positively. Winding alone cannot tell it from a real one.

## Measured against rust-geo, WASM to WASM

`tests/compare/rust/src/lib.rs` puts rust-geo behind this library's own flat ABI
and compiles it to wasm32, so the suite compares WASM against WASM in one Node
host, through one interchange format, at one timing boundary. Comparing our WASM
against a native Rust binary measured the toolchain as much as the algorithm.

rust-geo passes **18 of 26** against our 26, and is faster on every workload
where both finish. On the four workloads large enough to time reliably (WASM to
WASM, medians; the other 22 are under 3 ms and dominated by host noise):

| workload | ours (sweep) | rust-geo | GEOS |
| --- | ---: | ---: | ---: |
| parcels-union-1000 | 21.5 ms | 3.4 ms | 54.5 ms |
| parcels-union-4040 | 155.2 ms | 12.1 ms | 356.1 ms |
| complex-parcel-buffer-+2 | 59.2 ms | 46.9 ms | 6.9 ms |
| complex-parcel-buffer--2 | 57.9 ms | 57.4 ms | 11.6 ms |

Report medians move with machine state — GEOS itself measured 417 ms and 356 ms
for the same workload on two runs an hour apart — so treat the cycle counts in
"Where our own time goes" as the record of what actually changed, not these.

The reason is structural, not incidental. `geo`'s boolean operations delegate to
`i_overlay`, which works on `i_float::IntPoint { x: i32, y: i32 }` — a 32-bit
integer lattice whose scale is derived from the input's bounding box,
`ie = 29 - floor(log2(half_span))`. On this dataset that is `2^16`, a **15.3
micrometre lattice**. Integer arithmetic with no adaptive predicates and no f128
is where the speed comes from; snapping to that lattice, and the topology
collapses that follow, is where the errors come from. Area error against GEOS,
same host, same inputs:

| workload | ours | rust-geo |
| --- | ---: | ---: |
| parcels-union-100 | 0 m2 | 1.1e-3 m2 |
| parcels-union-1000 | 6.0e-8 m2 | 3.2e-1 m2 |
| parcels-union-4040 | 2.0e-6 m2 | 1.2e-1 m2 |
| parcels-buffer-100--10 | 3.6e-5 m2 | **4.9e+3 m2** |

### Where our own time goes

Profiled on `parcels-union-4040` (135,080 coordinates in, 3,080 out), native `ReleaseFast`, min of 7 runs, `rdtsc`:

| phase | before | after | |
| --- | ---: | ---: | --- |
| build events (267,046) | 38.3M | **11.3M** | reserve `p` and `e` up front |
| sort events | 52.9M | **22.0M** | bucket by x, compare only inside a bucket |
| sweep proper | 91.5M | 91.3M | unchanged |
| assemble rings | 4.1M | 3.8M | |
| **total** | **187.5M** | **128.0M** | **1.46x** |

Three findings, in order of size.

**The exact-predicate fallback was firing on degenerate input, not hard input.**
74% of `orient` calls on the since-removed graph engine and 97.9% on the sweep failed the
roundoff filter and ran the full error-free expansion — and *every one of them*
(1,737,059 of 1,737,063) had two of its three points bit-identical. Adjacent
parcels share vertices, so the determinant is exactly zero and the filter, which
is a relative bound, cannot certify a zero. Three vector compares in front of
the expansion took the sweep from 311 ms to 198 ms. Only 4 calls in the whole
workload are genuine near-ties. i_overlay never meets this: on a lattice a shared
vertex is an integer equality, and its `cross_product` is one exact `i64`
multiply-subtract with no filter and no fallback at all.

**The event arrays were being copied through every doubling.** `p` and `e` grew
by reallocation while 267,046 events were appended. The edge count is known
before the first event is made, so one `ensureTotalCapacity` pair cuts the build
phase by 3.4x. `overlay.zig` had the same shape, plus an unreserved
`point_map` that rehashed every node through each growth.

**The sort now compares almost nothing.** `sortEvents` maps x linearly onto
`ids.len / 2` buckets, counting-sorts into them, and runs `pdq` with the exact
comparator only inside a bucket. The map is monotone, so equal x always lands in
one bucket and bucket order is key order; a degenerate spread falls back to a
plain `pdq`. 2.4x on the sort phase, and worst-case behaviour is the old
behaviour plus one linear pass.

### Three more, after the engine removal

**`normalize` was 25% of a union, and 94% of that was `f128`.** It called
`predicates.area`, whose `f128` multiplies are `__multf3` libcalls — two per
vertex, 270,000 of them on 135,080 coordinates. Both callers only ever want the
*sign*, so `predicates.areaSign` filters in `f64` against a proven roundoff bound
and falls back to `area` when the bound cannot separate the sum from zero.
**48M cycles to 2.9M, 16x**, and `unionAll` end to end from 190M to 142M. The
exactness is unchanged and `predicates.zig` has a test that drives the fallback.

**The buffer stopped unioning a single polygon with itself.** 37% of the work on
`complex-parcel-buffer`, and it was also *wrong*: GEOS builds offset curves from
the raw rings, so the union pass made us disagree with GEOS on every
self-intersecting input. Now matching GEOS to nine decimals on all of them.

**The graph engine is gone**, which is the largest change by size: WASM 175,702
to 110,394 bytes, 65,222 to 43,209 gzipped.

Where that leaves the two comparisons that matter, 11 repeats:

| workload | before | after | GEOS | rust-geo |
| --- | ---: | ---: | ---: | ---: |
| parcels-union-4040 (wasm) | 161.3 ms | **137.8 ms** | 377 ms | 12.6 ms |
| complex-parcel-buffer-+2 (wasm) | 61.9 ms | **33.3 ms** | 7.5 ms | 47.6 ms |
| complex-parcel-buffer--2 (wasm) | 59.2 ms | **33.9 ms** | 12.0 ms | 61.3 ms |

We now beat GEOS on every union (**3.1x** on the largest, and GEOS pays no
codec while we pay WKB) and, for the first time, **beat rust-geo on
`complex-parcel-buffer`** — 1.4x and 1.8x — the one workload where its lattice
buys it nothing.

### What was tried and did not pay

Each measured on the same workload, same method:

| change | result |
| --- | --- |
| Sort a 24-byte record carrying the key inline, instead of a permutation of indices | sort **70.6M**, worse than 52.9M — `pdq` then swaps 24 bytes instead of 4, which costs more than the indirection it removes |
| Compare the dense coordinate array in `eventLess` rather than `Event.key` | sort 52.1M, ~4% and inside the noise |
| Dense far-endpoint array so `segmentLess` and `shares` never load an `Event` | build +5M, sweep −2M, net worse |
| Fuse both endpoints into one 32-byte `p` record | sweep unchanged, build +5M, net worse |

The last three all attack memory traffic in the hot predicates, and none of them
move the sweep phase at all. Whatever the sweep is bound by, it is **not** the
cost of fetching endpoints; do not spend another round on cache layout there.
The phase has not been broken down further than that — 91.3M cycles across
267,046 events is 342 cycles per event, and only ~3.8M exact-predicate
evaluations happen in it, so the predicates alone do not account for it.

### The status line does not want an index

Measured over one run: **402,601 `statusSeek` calls** at 7.0 `segmentLess` each
(~2.8M evaluations), **958,610 `shares` calls**, and **17.4M `u32` element
shifts** from ordered insert and remove. `statusSeek` is already a binary search, and the
status line holds a **mean of 124 entries, max 218** — so a seek is 7
cache-friendly probes into a 1 KB array, and an insert is a ~500-byte memmove the
compiler vectorises. A balanced tree or skip list would replace those 7 probes
with 7 pointer hops to make the memmove O(log n), and at this size that is a
losing trade. Revisit only if a workload pushes the status line past ~1,000.

### The complex-parcel-buffer outlier

Measured, not guessed. For the 19,208-coordinate parcel:

- The offset curve is **not** an explosion: 19,208 coordinates in, 32,031
  segments out, 1.67x. The "10,857 closed paths" note in `offset.zig` describes
  the *retired* decomposition and should not be read as current.
- Turning on JTS's default input simplification (`simplify_factor = 0.01`) cuts
  the curve 18% and the time 15% — 71.8M to 61.2M cycles. **Simplification is
  not the explanation**, and the accuracy it costs is still not worth it.
- Cost per event is essentially the same as the big union: **700 cycles/event
  for the buffer against 682 for `parcels-union-4040`**. Our buffer is not
  pathological; GEOS is simply much faster at this shape and much slower at
  unions (GEOS runs ~4,300 cycles/event on `parcels-union-4040`).

The structural difference is that GEOS does not route a buffer through a general
overlay. JTS's `BufferBuilder` nodes the offset curve with a **snap-rounding**
noder and labels depth on that graph directly. We node exactly and then run the
same two-operand overlay the union uses. That is the documented policy
divergence in `docs/BUFFER_APPROACH.md`, and it is what the outlier costs.

**One unforced cost is ours, though.** `bufferInput` calls `unionAll` on the
input before generating any curve. On this single-polygon workload that pass is
38,402 of the 102,464 events the buffer spends — **37% of the work, to union one
polygon with nothing**. Skipping it when the input is a single polygon would be
the largest single win available on this workload. It is a contract question,
not just an optimisation: `unionAll` currently also normalises orientation and
is where invalid input would be caught, so this is written down rather than
done.

### `normalize` is 28% of a union

`operations.unionAll` on `parcels-union-4040` costs 178.6M cycles end to end
while `sweep.execute` inside it accounts for 128.0M. The other ~50M is
`normalize` — ring validation, repeated-point removal and orientation forcing.
It has not been profiled or optimised at all, and it is now a larger slice than
the event sort.

### Vectorisation, revisited

`orient2` is already 2-wide, which is the whole of `simd128`. The independent
`shares` tests along a status run could go 4-wide, but only on native AVX2, and
the browser is 90% of the target. This agrees with the measurement already in
`CLAUDE.md`: a build with `simd128` removed runs within noise of one with it.
The wins above are all cache and comparison-count wins, not lane-width wins.

the documented filament ring, not a dropped feature.

neighbour set and the bounding box changes, so the scale changes, so the answer
changes. This library has no lattice.

Browser size, both import-free, rust-geo given the smaller surface (union and
buffer over polygons only, two exports) and built `opt-level="z"` with LTO and
`panic=abort`: rust-geo **200,365 raw / 67,180 gzipped**, ours **173,375 /
64,537** with four boolean operations, buffer, every standard shape and the full
ABI.

## Buffer parity: already there

Checked against `geo` 0.33.1 rather than assumed. Its `Buffer` is implemented for
Line, Rect and Triangle as well, but those are geo-types conveniences, not
geometry types: `Rect::buffer` and `Triangle::buffer` call `to_polygon()` first,
and `Line` is a two-coordinate LineString that degenerates to a Point. Every one
of those forms already goes through this library, verified against GEOS:

| input | relative symmetric difference |
| --- | ---: |
| Point, MultiPoint, LineString, MultiLineString, GeometryCollection | 0 |
| LineString of two coordinates (geo's `Line`) | 0 |
| LineString of one repeated coordinate (geo's degenerate `Line`) | 0 |
| Polygon (geo's `Rect`, `Triangle`), Polygon with hole, MultiPolygon | <= 3.6e-17 |

There is no parity work to do. An earlier note here claiming rust-geo covered
more shapes was counting Rust struct conveniences as geometry types.

## Targets and the ABI

The browser is **90%** of the target and is size-sensitive; a **Python module**
is the other 10%. Both speak flat coordinates natively — OpenLayers stores
`flatCoordinates` plus ends, and Shapely's `to_ragged_array` returns coordinates
plus ring and polygon offsets — so the library carries one representation and
hosts convert.

The two artifacts now have different surfaces:

| | exports | size |
| --- | ---: | --- |
| `zig build wasm` (`src/abi.zig`) | 8, flat only | 173 KiB raw, 64.5 KiB gzipped |
| `zig build native` (`src/native.zig`) | 16, flat + WKB | — |

WKB left the browser build: measured at 13.9 KiB raw and 4.2 KiB gzipped, nine
exports, and the only error-prone ownership contract in the API. It stays native,
where GeoParquet, PostGIS and the comparison suite need it and where a Python
module would link.

**All four boolean operations are in.** `geometry.Mode.covers` is the entire
difference between them, because the overlay already carried a winding counter
per operand; `operations.boolean` puts the subject in layer 0 and the clip in
layer 1. The ABI takes them through one entry point,
`geom_flat_execute(op, subject, distance, steps)`, so the next operation costs a
`Mode` value rather than an export — the surface got *smaller* while gaining
three operations.

Still to do here:

- [ ] **Symmetric difference and intersection are untested against GEOS.** The

- [ ] **`prepare.py` and `run.py` still drive the native library through WKB.**

## Integration target: MapLibre GL JS

Examined against maplibre-gl 6.9.0 and `@maplibre/geojson-vt`. Its boundary is
**GeoJSON and nothing else** — `setData` takes an object or a URL, there is no
flat or binary entry point, and the source is always WGS84 longitude/latitude.
Internally `geojson-vt` converts to flat `(x, y, z)` triples in normalised
Mercator inside a worker, but that is private.

So MapLibre cannot consume this library's arrays directly the way OpenLayers can.
The host converts. That is the right split, and the measurements say the
conversion does not matter:

| workload | result coordinates | host builds object + structured clone |
| --- | ---: | ---: |
| parcels-union-4040 | 3,080 | 0.89 ms |
| parcels-union-1000 | 1,219 | 0.31 ms |
| parcels-buffer-100 | 304 | 0.07 ms |
| complex-parcel-buffer | 31,338 | 8.02 ms |

Union and buffer **shrink** their input — 135,080 parcel coordinates union to
3,080 — so what reaches `setData` is small. A GeoJSON text writer inside the
library was built and measured against this: it was *slower* on the main thread
(1.01 ms against 0.89 ms; 9.87 against 8.02) and cost 15 KiB gzipped in the
artifact, because `std.fmt`'s float formatting is not free. It was removed.

Worth knowing for a host that does hit a large payload:

- `setData(url)` moves fetch and parse into the worker. A blob URL over bytes
  the host already has costs one copy and takes `JSON.parse` off the main
  thread — 7.8 ms for the 31,338-coordinate result.
- `updateData(diff)` sends only added, removed or updated features by id. For a
  buffer slider redrawing one feature this beats resending anything.
- Custom protocols resolve through `util/ajax.ts`, which the worker uses, so an
  MVT vector source would bypass `geojson-vt` altogether. That needs tiling and
  integer quantisation this library does not have, and is only worth it for data
  far larger than an overlay result.

## What gated dropping "experimental" — resolved 2026-09-15

The label is off. Grouped by what it promised, with what closed each. The
performance items further down were never blockers.

What is **not** claimed by removing it: that every valid input succeeds. 4 of
3,946 cluster unions still return `UnnodableCrossing`, and the README says so in
its own section rather than in a footnote. The label came off because that
limitation is understood, measured, bounded and documented — not because it went
away.

Still open, and neither blocks the label:

- **Calibrate the limits.** `max_work`, `max_nodes` and `max_output_points` are
  round numbers rather than figures derived from the envelope. They are enforced
  and conservative, so this is precision, not safety.
- **A distinct ABI status for `UnnodableCrossing`.** It shares `5` with
  malformed input; the Zig API already distinguishes them.

### 1. The public API has to stop changing

- [x] **`grid_size` removed.** It was accepted by `UnionOptions`, `BufferOptions`
      and the WKB ABI and then always rejected with `InvalidOptions`. It is gone
      from all three, along with the `geom_union_with_options` export that
      existed only to carry it. Precision reduction can come back later as a
      feature with a design behind it. No dead parameters remain in the surface.

### Settled: the safety checks stay

`ReleaseFast` was measured against the shipped `ReleaseSafe` build, same process,
same inputs, 9 repeats: **1.11x faster, 15 KB larger raw, and bit-identical
output** on every workload, plus 26/26 on the differential suite. The optimiser
inlines more than the checks occupy, so dropping them loses on size as well as
on safety. `build.zig` keeps `-Dwasm-optimize` so the measurement can be redone;
the default does not change.

### 2. Resource safety, because a browser tab is the target

**The 104 MiB figure below was stale; re-measured 2026-09-15 through the flat
ABI, reading `memory.buffer.byteLength` after each call.** The complex parcel
buffer peaks at 25.7 MiB, not 104, and the largest union is the real worst case:

| `parcels-union-100` | 936 | 2.1 MiB | 2.26 |

**The fallback path costs about 3x per coordinate** because it runs the overlay
twice more over a larger, fully-noded path set. That is ~260,000 coordinates of
headroom, and it is the number that actually gates the promise, because nothing
tells a caller in advance whether their input will take that path.

- [x] **Two allocation fixes, worth 2.3x on the path that needed it most.**

- [x] **No leak across calls.** Eight repeats of the same workload hold flat at

- [x] **Published the envelope.** README has "Memory, and what size input this

- [ ] **Calibrate the limits.** `max_work`, `max_nodes` and `max_output_points`

### 3. Behaviour on messy input — decided

- [x] **Invalid geometry is rejected, and that is the documented policy.** A
      degenerate ring, a ring with fewer than four points, or an out-of-range
      coordinate returns an error. Nothing is snapped, clamped or collapsed to
      make a call succeed. The README's "Invalid input" section states this as a
      deliberate divergence from JTS/GEOS, with the trade table, and points
      callers at `make_valid` / `ST_MakeValid` / `GeometryFixer` upstream.
      Repair tooling is explicitly somebody else's job.
- [x] **Snap-rounding declined.** JTS and GEOS retry on progressively coarser

      Same decision as above, recorded for the same reason: a snapped result
      answers a slightly different question than the one that was asked.

This costs 3 of 158 JTS assertions, all degenerate rings, and it is why the

### Chunking: what it can and cannot do here

The question is whether a windowed or tiled overlay removes the WASM memory
ceiling. Measured rather than argued:

**Host-level cascading already works, today, with no library change.**
`unionAll` is n-ary and associative, so a host can fold in batches. Folding the
4,040 parcels in batches of 500 or 1,000 returns **the same 3 polygons and
bit-identical area** as the one-shot union.

| | polygons | area | peak | batch failures |
| --- | ---: | ---: | ---: | ---: |
| one shot | 3 | 338046121.626241 | 81.8 MiB | — |
| batches of 1,000 | 3 | 338046121.626241 | 67.5 MiB | 0 |
| batches of 500 | 3 | 338046121.626241 | 71.4 MiB | 0 |
| batches of 250 | 955 | 338046467.165185 | 71.2 MiB | **4** |

Two findings, and the second is the important one:

1. **It buys 13-18%, not an order of magnitude.** The peak is set by the largest
   single call, and a cascade still has to merge everything eventually.
2. **Smaller batches make correctness worse.** At 250 the cascade hit four
   `UnnodableCrossing` failures and returned the wrong answer, on input the
   one-shot union handles. Chunking multiplies the number of overlay calls and
   every one carries the ~0.1% exposure from gate 6 — and a subset's local
   geometry is not easier than the whole, it is just different. Any chunking
   recipe published here has to say that.

**Streaming the sweep** — the "window of nodes" idea — is sound in principle:
the status line is already a window, and the residency is an artefact of how
results are collected, not of the algorithm. It would need result edges emitted
at their closing event, rings assembled incrementally as chains close, and
hole-to-shell nesting resolved through recorded chain ids instead of the `prev`
pointers into the event array. Worst case stays O(n) — one ring spanning the
whole sweep keeps its whole chain open — and it costs the graph-labelling
fallback and `renodeOnce`, both of which need the finished arrangement. Those
only run on failure, so they could stay non-streaming.

**Do the constant factors first.** Two allocation fixes above took the fallback
path down 2.3x in an afternoon, and `Event` is still 64 bytes. Streaming is a
large architectural change against a peak that is, right now, only a quarter
arrangement.

### 6. Valid input can still fail, and the README does not say so

`error.UnnodableCrossing` — 4 of 3,946 cluster unions, 0 of 57,990 cluster
buffers — is raised on input that is **valid**. The README's only mention of a
noding failure sits in the "Invalid input" section, in a table row that reads
`Noding failure | error | retries on coarser grids`, framed as a consequence of
bad geometry. A caller who reads that concludes that clean input always
succeeds. It does not.

This is a documentation gate, not a code one: the behaviour is deliberate and
the alternative is snap-rounding, which is already declined above. What is
missing is a sentence saying that a valid union can return an error, at roughly
what rate, and what a caller should do about it.

- [x] **Said in the README**, as its own section — "When valid input fails" —
      rather than buried in the rejection policy, with the measured rate, the
      cause, and what a caller can do. The invalid-input table now points at it,
      and the ABI status list says `5` covers both meanings.
- [ ] **Give it a distinct ABI status.** Documented for now, not fixed: a host
      still cannot tell "your geometry is broken" from "this arrangement is not
      representable in f64" without checking its own input, and those want
      different responses. The Zig API already distinguishes them
      (`error.UnnodableCrossing`); the flat ABI does not.

### 5. The buffer produces unclosed boundaries on ~0.6% of valid input

**Largely closed (2026-09-14) by the graph-labelling fallback — see "What
shipped" below. The investigation is kept because the remaining failures are the
residue of the same problem.** The record from here to that section is the
original diagnosis, written before the fix.

`bufferAll` returns `error.NodingFailure` from `sweep.zig`'s contour walk on
valid input with default options. Two minimal cases:

- two axis-aligned rectangles `(0,0)-(2,1)` and `(2,2)-(3,3)` buffered by `+1`,
  where `unionAll` on the same two rectangles succeeds;
- the L-shape `(1,0)(3,0)(3,3)(0,3)(0,1)(1,1)(1,0)` eroded by `-1.25`.

Measured over ~300,000 random valid inputs: **0 failures across ~120k boolean
operations, 95 failures in ~15k positive buffers and 95 in ~15k negative
buffers** — about 0.6% of buffer calls. Reproducible across seeds.
`quadrant_segments` changes *which* cases fail, not *that* they do.

The cause is not noding. Instrumenting the L-shape just before the contour walk
shows **3 chosen edges, 4 vertices, 0 unnoded crossings, and 2 vertices of
degree 1** — the crossings are all found. It is the transition labelling in
`resolve`/`enter` marking a set of result edges that is not a closed boundary,
and `walk != start` is only where it surfaces. A larger case shows a vertex with
`in = 2, out = 1`, so the radial rays do not alternate, which they must for any
boundary.

**GEOS does not have this bug, and its retry ladder is not why.** Every one of
24 randomly found inputs that qdgeo cannot buffer, GEOS buffers correctly — and
it does so on the *first* attempt, at full double precision. The output carries
irrational arc vertices with full mantissas and nothing lands on a coarse grid,
so `bufferReducedPrecision` never ran. Snap rounding is irrelevant here; the
difference is structural.

JTS/GEOS build a `PlanarGraph` in which **both directed edges of every edge
exist by construction** (`DirectedEdge` pairs), propagate depth over connected
subgraphs seeded by ray casting, and keep edges where depth crosses 0/1. Degree
balance is therefore guaranteed before any boundary is traced. qdgeo labels
transitions during the sweep and then traces contours, relying on the radial
ray-sort in `emit` to pair incoming with outgoing edges — so a labelling that
marks a non-closed set has nothing to catch it until the walk runs off the end.

### The paired assembly was prototyped: free, but not sufficient

**Cost: none.** Storing both directions of each result edge, twin at `e ^ 1`,
and replacing the backward ray search with the half-edge rotation rule measured
**157.9M cycles against 157.3M** on `parcels-union-4040`, with byte-identical
output. The ray count does not change — the current form already stores two rays
per undirected edge — and each ray shrinks from an 8-byte record to a `u32`,
while `next` becomes one lookup instead of a scan. Speed is not the obstacle.

**It does not fix the defect.** With pairing, every half-edge has exactly one
successor and the successor map is a permutation, so every walk closes and
`NodingFailure` disappears. But on the two-rectangle case the result came back
as **0 polygons instead of 17.70** — every traced ring classified as a hole. The
loud failure became a silent wrong answer, which for this library is strictly
worse. The single-square buffer stayed correct (15.1365), and the L-shape
erosion became correct (0.0), so it is not uniformly wrong either.

That is the useful result: **pairing is necessary but not sufficient.** It makes
the walk survive an inconsistent labelling instead of catching it. The defect is
upstream, in what `resolve`/`enter` mark as a transition, and it has to be fixed
there first. Pair afterwards, for free, to make degree balance structural.

Prototype kept out of the tree deliberately; reproduce it from this note.

### Where the labelling goes wrong, exactly

Instrumented the two-rectangle case at `quadrant_segments = 1`, which fails the
same way as 16 and is small enough to read. The buffer overlay produces **12
chosen edges over 13 vertices, with exactly two imbalanced**:

```
IMBALANCE v5 (1,2) in=0 out=1
IMBALANCE v6 (1,3) in=1 out=0
```

The edge **(1,3) → (1,2) is missing** — the left side of the second rectangle's
offset curve. Its transition resolved to 0, so it was never chosen. Every other
edge of both curves is present and correctly signed.

The geometry is a **T-junction**: rectangle 1 `(0,0)-(2,1)` buffered by 1 has its
top edge along `y = 2`; rectangle 2 `(2,2)-(3,3)` buffered by 1 has its left edge
along `x = 1` running from `y = 2` up to `y = 3`. They meet at exactly `(1,2)`,
one curve's endpoint landing on the other curve's interior. The segment above
that junction is outside rectangle 1's buffer and must be kept; it is dropped.

The failure reproduces at every `quadrant_segments` from 1 to 16, so it is not an
arc-resolution artifact.

### What `below` actually means

Derived from the code and confirmed by tracing, after five failed repairs. Write
this down before touching it again.

**`below` is a snapshot over the segment's own span, and it must survive
removals.** It is the winding beneath the segment when it was inserted, and
`resolve` reads it back at the closing event. Making it live — decrementing when
a segment underneath is removed — destroys exactly the information `resolve`
needs, because the segments under it routinely close in the *same batch*. Traced
on two disjoint rectangles: the bottom edge closes first, the decrement strips
its `+1`, and the top edge then resolves with `below = {0,0}` where the
rectangle's interior should give `{1,0}`. Its transition comes out 0 and the
whole top edge vanishes. Every one of the 23 tests fails this way.

**Two relations are in play and they are not the same** — but this is *not* the
cause of the known failures. `enter` walks down past everything the new segment
`shares` with (collinear and overlapping in more than a point) and excludes that
run from `below`; `resolve` sums back only the run it `sameSegment`s with
(identical endpoints). `sameSegment` implies `shares` but not the reverse, so a
partial collinear overlap would have its delta excluded and never restored.

That asymmetry is real and worth closing on its own. It is **not** what breaks
the buffer. Instrumented at every `resolve`, counting neighbours that `shares`
without `sameSegment`:

| case | result | partial | exact |
| --- | --- | ---: | ---: |
| union, shared edge | ok | 0 | 1 |
| buffer +1, the failing case | `NodingFailure` | **0** | **0** |
| buffer -1.25, L-shape | `NodingFailure` | **0** | **0** |
| buffer +1, single square | ok | 0 | 0 |

**The failing cases contain no coincident segments at all.** Coincidence is a
red herring for them; the remaining suspect is the T-junction, where a vertex of
one curve lands on the interior of another's edge and the vertical segment above
it opens and resolves in nearby batches.

**Insert-only maintenance double-counts.** Keeping the snapshot through removals
but folding each newly inserted segment into the windings above it gives
`below = {2,0}` where `{1,0}` is right, so the interaction with `enter`'s own
run-summation is not a simple addition either.

### Five fix attempts that did not work

`Event.below` is the winding cached beneath a segment **when it was inserted**,
and `resolve` reads it back at the closing event. The obvious theory is
staleness: a segment inserted *underneath* an active one changes what is beneath
it, and the cached value never learns. `resolve`'s own comment half-admits this
for coincident bundles.

Acting on that theory failed three times, each breaking 16 of 23 tests:

1. Maintaining `below` incrementally — add the newcomer's delta to every
   segment above on insert, subtract on remove.
2. The same, but starting above the coincident run rather than at the next
   index, since `enter` steps over a bundle and `resolve` sums it separately.
3. A pure diagnostic: ignore the cache entirely and recompute the winding below
   by walking the whole status line at resolve time. Obviously correct under the
   prefix-sum model, far too slow to ship, and it **still broke the same 16
   tests**.
4. Redefining `below` as live and absolute — winding strictly below in status
   order, maintained on both insert and remove — with `resolve` reading the two
   ends of the run instead of re-summing. Broke all six union cases, including
   two rectangles that do not touch at all.
5. The same, but shifting only on insert. `below = {2,0}` where `{1,0}` is
   correct.

The useful part is the diagnosis above, not the attempts. A repair has to satisfy
three constraints at once: survive removals within a batch, reconcile `shares`
with `sameSegment`, and not double-count against `enter`'s run summation. None of
the five did all three.

### What JTS does instead, read from the source

`node_modules/jsts` is the JTS algorithm in readable JavaScript. Two things in
`operation/buffer/BufferBuilder.js` are worth copying, and one is worth copying
*first*.

**1. Noding and labelling are separate passes, and noding finishes first.**

```js
this.computeNodedEdges(bufferSegStrList, precisionModel)
this._graph = new PlanarGraph(new OverlayNodeFactory())
this._graph.addEdges(this._edgeList.getEdges())
const subgraphList = this.createSubgraphs(this._graph)
this.buildSubgraphs(subgraphList, polyBuilder)
```

Nothing is labelled until every edge exists. qdgeo interleaves the two: a
segment's transition is decided at its closing event, from state captured at its
opening event, while the sweep is still discovering geometry. That is the
structural difference, and it is why a repair has to satisfy three constraints at
once instead of none.

**2. Duplicate edges are merged before labelling, not reconciled during it.**

```js
insertUniqueEdge(e) {
  const existingEdge = this._edgeList.findEqualEdge(e)
  if (existingEdge !== null) {
    let labelToMerge = e.getLabel()
    if (!existingEdge.isPointwiseEqual(e)) { labelToMerge = new Label(e.getLabel()); labelToMerge.flip() }
    existingLabel.merge(labelToMerge)
    existingEdge.setDepthDelta(existingEdge.getDepthDelta() + BufferBuilder.depthDelta(labelToMerge))
  } else { ... }
}
```

`findEqualEdge` keys on an `OrientedCoordinateArray` over the edge's *whole*
coordinate list, so it only ever matches exact duplicates — and that is enough,
because the noder has already split every collinear overlap into pieces that are
either identical or disjoint. One edge per geometric location, carrying the
summed delta. There is no `shares`-versus-`sameSegment` question to get wrong
because coincidence does not survive into the labelling stage.

That is the fix for the asymmetry above: **merge coincident segments at
subdivision time and sum their deltas**, rather than carrying a run through the
status line and reconciling at `resolve`. It will not fix the known failures —
they contain no coincident segments — but it removes a whole class of latent
divergence and simplifies `enter` and `resolve` to the point where the remaining
bug is easier to see.

**3. Depth is seeded by ray casting, once per subgraph.**
`buildSubgraphs` takes each subgraph's rightmost coordinate, asks
`SubgraphDepthLocater` for the depth there by counting the subgraphs already
placed, then `computeDepth` propagates across the whole subgraph and
`findResultEdges` keeps the 0/1 crossings. The seed is a single global fact; the
rest is propagation over a finished graph. Nothing depends on insertion order.

### Cost of adopting the JTS approach, measured before building it

JTS builds its `PlanarGraph` over **every noded edge**, not just the ones that
reach the result. Counting both on real workloads:

| workload | noded segments | result segments | ratio |
| --- | ---: | ---: | ---: |
| `parcels-union-4040` | 133,523 | 2,636 | **50.7x** |
| `complex-parcel-buffer` | 32,157 | 31,329 | **1.0x** |

Assembly is currently ~2.6% of runtime measured over the *result* edges. Scaling
it by those ratios means:

- **Buffers: essentially free.** Almost every noded segment is already a result
  segment, so graph-based labelling costs nothing extra — and buffers are where
  the defect is.
- **Unions: roughly doubles the total.** 50x the assembly work on a stage that is
  2.6% lands near 130% of current runtime. That is very likely why GEOS takes
  447 ms on this union against qdgeo's 156 ms while being comparable elsewhere.

So "node fully, merge duplicates, label over the graph" is **cheap exactly where
it is needed and expensive exactly where the current design already works**
(0 failures in ~120k boolean operations). The obvious shape is to graph-label
only when the result/noded ratio is high, but two labelling paths means two
chances to be wrong, and the streaming path would still own the union case.

### Two labelling paths: measured, and the split is not "buffer vs boolean"

The ratio across all 26 workloads is not an operation property, it is a
**cancellation** property:

| workload | ratio | |
| --- | ---: | --- |
| `parcels-union-4040` | 50.7x | adjacent parcels, boundaries cancel |
| `parcels-union-1000` | 15.8x | |
| `parcels-union-100` | 11.1x | |
| `parcels-buffer-100-*` | 2.9-3.4x | **a buffer, but the cost is its internal union pass** |
| `complex-parcel-buffer-*` | 1.0x | offset curves barely cancel |
| single-shape buffers, small unions | 1.0-2.2x | |

So `parcels-buffer-100` is a buffer at 3x, not 1x: `bufferInput` unions its input
first, and that pass is the expensive kind. Splitting per *operation* would put
graph labelling on exactly the wrong pass.

**This turned out to be the wrong conclusion, and measurement is what said so.**
Splitting per overlay call assumes the choice can be made from the call site.
It cannot: what decides is whether *this particular arrangement* came out fully
noded, which nothing upstream knows. See "What shipped" below — it is a
fallback, not a split.

### What shipped (2026-09-14)

`sweep.execute` now tries the sweep's own labelling and **retries the whole
overlay with the graph labelling when the first attempt returns
`NodingFailure`**. Callers see one function with the signature it always had;
`operations.zig` passes no mode and neither ABI exposes one.

Why a fallback and not a split:

| workload | `.sweep` only | `.graph` only | fallback |
| --- | --- | --- | --- |
| 57,990 cluster buffers (2-16 parcels, 5 distances, q = 1/4/16) | 10 fail | 6 fail | **6 fail**, +2.9% time |
| 3,946 cluster unions | 4 fail | 4 fail | **4 fail**, no cost |
| 315,120 single-parcel buffers | 0 fail | 0 fail | 0 fail |
| `parcels-union-4040` | passes | **fails** | passes |
| two rects `+1`, L-shape `-1.25` | **fail** | pass | pass |

Neither labelling dominates, so neither can be pinned at a call site. Order is
decided by `parcels-union-4040`: `.graph` cannot label it at all, and running
`.graph` first would also pay a second pass on every call that never needed one.
Running it second costs nothing except on inputs that already had no answer.

Both minimal reproductions above now match GEOS exactly — 16.0 and
17.704822735818908 for the two rectangles at `q = 1` and `q = 16`, and empty for
the eroded L — and are pinned in `src/tests.zig`.

### Why `.graph` cannot label the 4,040-parcel union

Because that arrangement is not fully noded, and a wedge model assumes it is.
Reduced to **five parcels** by delta debugging against the oracle "sweep passes
and graph fails", then instrumented: 63 segments, 57 after duplicate merging,
52 vertices, **3 unnoded crossings**, 0 partial collinear overlaps, 0 vertices
of degree 1. Every one of the three is the same shape — a vertex pair about
2e-9 apart, where the sweep split one segment at a computed crossing and the
rounded split point landed off the other segment's line:

```
(6233.019441406742,-1529.5273384991378)-(6233.964433039578,-1630.3343262662754)
  crosses
(6233.964433037561,-1630.3343262662754)-(6233.964433039578,-1630.3343262662609)
```

This is the failure GEOS answers with snap-rounding, which qdgeo does not do.
The sweep's own labelling survives it because it never builds a planar
arrangement: it reads the transition off the status line, whose order stays
self-consistent whether or not the geometry agrees.

### Three bugs the graph pass had, and what each cost

Each was found by a failing test, not by reading:

1. **Seeded at the wrong place.** Seeding any vertex makes the ray cast
   ambiguous. Seeding each connected component's *rightmost* vertex makes it
   exact, because nothing of that component reaches past it.
2. **Signed the wedge step by the wrong axis.** Crossing a segment
   counter-clockwise is *upward* when the segment's counter-clockwise normal
   points up — which is a test on the direction's **x** component, not its y.
3. **Gave the transition to the wrong member of a coincident run.** `enter`
   records `prev` as the status entry below a run, so the nesting walk only ever
   lands on a run's topmost member. `resolve` marks that one `carries`; the
   graph pass has to agree, or `below` comes back `none` and nesting fails.
   This one cost three of the four test failures the first working version had.

And one fix that was not a bug in either pass: merging coincident edges before
labelling, JTS's `insertUniqueEdge`. Without it two duplicates leave a
zero-width wedge between them and the winding either side is wrong.

The 6 remaining cluster-buffer failures and the figure-eight line buffer were

`execute` now does exactly that after both labellings fail.

| | before | after |
| --- | --- | --- |

Cost, measured on the failing inputs at `ReleaseSafe` (median of 9):

| case | no retry | one pass | outcome |
| --- | ---: | ---: | --- |
| `buf-k8-s1280-d5-q1` | 0.27 ms | 0.89 ms | rescued |

**A call that succeeds pays nothing** — the retry is after the first attempt

### Why the 4 cluster unions cannot be fixed by noding at all

They are already at a **noding fixpoint**: 847 segments in, 847 out, pass after
pass, with no growth at any iteration up to 8. Instrumented at the fixpoint,
each holds exactly **1 crossing, and it is unsplittable** — the exact
intersection, rounded to f64, lands on or past an endpoint of one of the two
segments. `divide` refuses it and is right to: putting a vertex there would move
the crossing off the other segment's line. No iteration count reaches it.

`Engine.lost` counts these during the sweep, and `execute` now raises
`error.UnnodableCrossing` rather than `NodingFailure` when any were seen. Both
map to ABI status 5, so nothing host-visible changed, but the Zig-level error
now separates a precision limit from a bug.

Its value as a *predictor* was tested and is not good enough to act on:

| | lost > 0 | lost = 0 |
| --- | ---: | ---: |
| call failed | 4 | 6 |
| call succeeded | 1 | 61,925 |

The 4 are exactly the hopeless unions and the 6 exactly the rescuable buffers,
which looks like a perfect gate. It is not: the figure-eight buffer has a lost
crossing **and** is rescued by the re-noding pass. Gating the retry on `lost`
was implemented, measured, and reverted — it trades a real answer for time on
calls that error either way.

- [ ] **The 4 cluster-union failures.** Only snapping can close an unsplittable
      crossing: the two near-coincident vertices have to become one. That is the
      policy question in `docs/BUFFER_APPROACH.md`, not an algorithm gap, and it
      is 0.1% of cluster unions — the 4,040-parcel union itself is unaffected.

Two other symptoms trace to the same defect and will close with it:

- Buffering a closed LineString with **zero signed area** (a figure eight)
  fails. Splitting it into two open chains was tried and changes nothing — each
  chain buffers correctly alone and the pair fails when overlaid.
- `deduplicate` and the zero-ring guard in `bufferInput` fixed two *other*
  buffer failures found in the same review; those are done and tested.

## Making the performance instrumentation Zig-native

Every timing number in this file was produced by a throwaway Zig program with an
`rdtsc` counter, written and deleted each time. That is the part worth making
permanent. The rest of the Python is not about performance at all.

**Split the two concerns first.** 747 lines of Python do two unrelated jobs:

| job | files | can it be Zig? |
| --- | --- | --- |
| measure qdgeo's own speed | (none — ad-hoc probes) | **yes, easily** |
| compare answers against other implementations | `run.py`, `probes.py` | no, and it should not be |
| ~~run the JTS suite~~ | ~~`jts/run.py`~~ | **done — JSTS, not Zig** (see below) |

The comparison harness exists to run GEOS, JSTS, Turf, polyclip-ts and Rust Geo.
Those are Python and JavaScript by nature. Reimplementing the oracle in Zig would
mean grading our own homework.

### Low effort, high value: `zig build bench`

A permanent benchmark step reading a committed binary fixture and reporting
per-phase cycles. Roughly **150 lines and an afternoon**:

- `build.zig` step plus a `src/bench.zig` root — the probe shape used all
  session: `lfence; rdtsc`, min of N runs, per-phase counters behind a comptime
  flag so the shipped build carries none of it.
- Fixture as a flat block on disk, `@embedFile`d. The parcel dataset is 135,080
  coordinates, so ~2.2 MB. Generate it once from the GeoParquet with the existing
  Python and commit it, or write it next to the download in `fetch.py`.
- Output: cycles per phase (build, sort, sweep, assemble), which is what every
  optimisation in this file was judged on.

This removes Python from the performance loop entirely and makes the numbers
reproducible by `zig build bench` rather than by reconstructing a probe.

### Done, and not the way this section predicted: the JTS runner

The analysis below was right that the runner needed only a WKT parser and a
topological equality test, and right that writing both in Zig was a bad trade.
It missed the third option.

> ~~`tests/jts/run.py` is 311 lines and needs only two things from Python: a WKT
> parser and a topological equality test. A Zig WKT reader is ~300 lines for the
> 2D types qdgeo supports. Equality is harder — it currently delegates to GEOS,
> and replacing it with area plus Hausdorff in Zig is another ~200 lines and a
> weaker check. **About a week, and it trades away GEOS as the arbiter.**~~

**JSTS already had both, and it is JTS.** The runner is now
`tests/jts/jts.test.mjs`, and the reference side — WKT reading, `equalsTopo`,
area, `DiscreteHausdorffDistance` — is JTS's own code ported to JavaScript.
That is a *better* arbiter than GEOS for a suite whose entire claim is fidelity
to JTS, not a weaker one, and JSTS was already a dev dependency because the
comparison suite measures it. The XML is four element names deep and is read in
`tests/jts/cases.mjs`; it never needed a parser library.

It also moved the suite from the native `.so` to the shipped WASM artifact
through the shipped binding, so the thing under test is the thing that ships.
Same 155 passing assertions. One case shifts from 3 failures to 3 skips because
JTS's own `WKTReader` refuses a three-point LinearRing where Shapely allows it —
which is JTS's answer to that input, so the suite now reflects it.

Afternoon, not a week. Python is gone from the correctness path entirely.

### Not advisable: the differential suite

`prepare.py` also reads GeoParquet (`pyarrow`) and reprojects (`pyproj`), neither
of which has a mature Zig equivalent, and `run.py`'s adjudicator needs exact
rational arithmetic (`fractions.Fraction`) that Zig's standard library does not
provide. Porting that is weeks of work to remove a dependency that only test
tooling has.

**Recommendation:** do `zig build bench`, leave the rest. The benefit is not
fewer languages — it is that a performance claim becomes a command anyone can
run, instead of a probe that has to be rebuilt from a note.

The two processes are now split and documented in `TESTING.md`: correctness
needs Zig and Node and runs in about two seconds; comparison keeps Python
because Shapely *is* GEOS, and keeps Rust as an optional extra because
`tests/compare/rust/` builds only the rust-geo shim. `zig build bench` would
close the last gap — measuring qdgeo's own speed without the oracle present.
